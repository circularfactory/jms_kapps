Use case 2 — the monitor

It reads the graph, and in "graph + streams" the participants' handover event streams too, and writes nothing; its middleware registers it and sends its heartbeat.

How the monitor reads

Every view but Refusals comes from the monitor's reads of the graph, in both modes. In graph only the monitor sees what a dashboard sees that sees only the knowledge graph: it follows no participant's handover event stream, so it shows no refusal. In graph + streams it follows them too, for the Refusals view. The monitor reads the graph in the background at the interval set here, from 0.5 s to 10 s, whether a page is open or not; the refresh above only says how often this page asks the monitor what it read, which sends no query.

Topology

Drawn from the graph's connections. Each module is seen from above: a green frame, silver motor rollers that carry a box north–south, and dark belt strips between them that carry a box east–west. A dashed grey module is offline: it has no service with an address and a fresh heartbeat. A live module that holds a box is tinted blue, and an orange square is a box the module possesses.

Each connection, as the graph holds it, has an arrowhead where it leads, and a head at both ends where it leads both ways. A box that a module holds has a coloured disc with its number on its destination, which its transport names. The monitor draws no route to it: only the module that holds a box knows where it goes next, and it decides that again at every hop.

Handovers

Each handover the monitor saw by its commit: the box's possessor changed between two of its reads of the graph, a second apart, or a new box was on its origin, which the WMS handed it to. Newest first: when it saw it, the box, and from whom to whom. Only the newest are kept. A box handed over twice between two reads, which a transit time under a second allows, shows as one handover.

Possible deadlock

A module raises the deadlock alarm for a box it holds that has waited for a Reserve longer than the deadlock alarm time of its launch, 300 s unless the Launcher sets another, and reports it on its handover event stream, so only in "graph + streams". The notice names every module involved: each module with an alarm, and the modules it asks. It shows the alarms whose box the graph still shows on that module. The boxes keep waiting: an alarm fails nothing.

Refusals

The newest commits the triple store refused, newest first, as the participants' handover event streams report them, so only in "graph + streams": a refused write leaves no trace in the graph. Each result of the store's validation report is a row: what the store says, where, and which rule refused; a name shows its whole IRI when you point at it. The report itself is behind "report". A refusal that arrives while the page is open is highlighted for a few seconds.

Queries sent

Each SPARQL query the monitor sends, exactly as the store received it the last time it went: how often it goes now, when it went last, how long the store took to answer, and how many rows came back. The query for the live participants names the oldest heartbeat that counts, so its text changes from read to read. A poll of this page sends none. Its middleware's own writes, the registration and the heartbeat, are not reads of the monitor and are not listed.
