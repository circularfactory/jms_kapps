Use case 2 Monitor

It reads the knowledge graph, and the services' handover event streams too while the switch at Refusals is on. It writes nothing.

How the monitor reads

The monitor reads the knowledge graph in the background at the interval set here, from 0.5 s to 10 s. The refresh above only sets how often this page asks the monitor for what it read, which sends no query.

Topology

Drawn from the connections in the knowledge graph. Each module is seen from above: a green frame, silver motor rollers that carry a box north–south, and dark belt strips between them that carry a box east–west. A dashed grey module is offline: it has no service with an address and a fresh heartbeat. A live module that holds a box is tinted blue, and an orange square is a box the module possesses.

Each connection, as the knowledge graph holds it, has an arrowhead where it leads, and a head at both ends where it leads both ways. A box that a module holds has a coloured disc with its number on its destination, which its transport names. The monitor draws no route: only the module that holds a box knows where it goes next.

Handovers

Each handover the monitor saw by its commit: the box's possessor changed between two reads of the knowledge graph, or a new box appeared, which the WMS handed to its origin. Newest first: when the monitor saw it, the box, and from whom to whom. Only the newest are kept. A box handed over twice between two reads shows as one handover.

Possible deadlock

A module raises the deadlock alarm for a box it holds that has waited for a Reserve longer than the deadlock alarm time of its launch, 300 s unless the Launcher sets another, and reports it on its handover event stream, so the notice follows the switch "Follow the services' handover event streams" at Refusals. The notice names every module involved: each module with an alarm, and the modules it asks. It shows the alarms whose box the knowledge graph still shows on that module. The boxes keep waiting: an alarm fails nothing.

Refusals

The newest commits the triple store refused, newest first, as the services' handover event streams report them, so only while the switch is on: a refused write leaves no trace in the knowledge graph. Each result of the triple store's validation report is a row: what the triple store says, where, and which rule refused; a name shows its whole IRI when you point at it. The report itself is behind "report". A refusal that arrives while the page is open is highlighted for a few seconds.

Queries sent

Each SPARQL query the monitor sends, exactly as the triple store received it the last time it went: how often it goes now, when it went last, how long the triple store took to answer, and how many rows came back. The query for the live services names the oldest heartbeat that counts, so its text changes from read to read. A poll of this page sends none.
