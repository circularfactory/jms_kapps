Processes

One process for each module, the Warehouse Management System, and the monitor. A process is live while its service carries a fresh heartbeat in the graph. A process that does not stop in time is killed, and a kill skips its deregistration. Click a name for its recent output. Clear, beside Stop all, stops every process and then empties the dataset, graph by graph, after it asks; it clears nothing while another launcher's process is live there. The next launch loads the ontologies, the shapes and the topology again.

Each module has two fault switches. With skip-reserve it hands a box on without asking first, and the triple store refuses that when the next module holds a box. With complete-without-releasing, as a box's destination, it completes the transport before it gives the box back, which the triple store always refuses. The monitor shows each refusal, and the box still arrives. A module starts with both off.

Boxes on the station

Every box whose possessor is not the Warehouse Management System, with the module that possesses it, and its transport and that transport's status. The Launcher reads them with the one SPARQL query below, every second, whether this page is open or not, and the page shows what it read last; a poll of this page sends no query. The query is standard SPARQL: run it on the same dataset, in the store's workbench or in any other SPARQL endpoint, and you get the same list. The monitor's table of boxes shows these boxes too, beside those the Warehouse Management System possesses.

Topology

      
The modules that are running, and where each one hands boxes to. Launching
        clears the dataset, seeds the chosen topology, and restarts every process. To build a
        topology of your own, press Edit, which opens the editor on the chosen
        topology, Empty grid, or Upload, which opens it on a
        topology file: a module list, as the first iteration wrote one, and as the editor's
        Download saves one. At the command line,
        jms-uc2 --topology <path> starts on such a file. The two pickers
        Module strategy and WMS strategy choose, for the next
        launch, how each module chooses the neighbours it asks for a box, and how the Warehouse
        Management System picks where a box starts and ends: Real behaviour is the demonstration's,
        and a strategy whose name ends in "(synthetic)" makes traffic that a benchmark can
        repeat. With collect history checked, the next launch turns on the triple
        store's history collection, so that the possessor a box had at any earlier time can be
        read, as the reference page on past possessions shows. It starts at whether the launch
        that runs was launched with it: on where jms-uc2 --collect-history started the page, and off by default. A
        launch without it leaves the collection as it was. deadlock alarm (s) is
        how long a box that a module of the next launch holds may wait for a Reserve before the
        module raises the deadlock alarm for it, a warning in its output that starts with
        "possible deadlock:" and a notice on the monitor; the box keeps waiting. It starts at
        jms-uc2 --deadlock-alarm-seconds, 300 s by default.

      
      
      
      
      
      
The samples pair, tee, grid and merge-fault-demo run one way, from their
        entry modules to their exit modules. The merge-fault-demo is for the fault demo: a merge of
        two streams, where skip-reserve on Module5 collides with the box that waits on Module6. A
        topology is refused, before anything is cleared, where it has no module, or where it has a
        pure two-way corridor: a module whose only two connections both run both ways, where two
        boxes that meet head-on could wait for each other forever, with no neighbour to step aside
        to. Any other topology loads, two-way connections too: a module takes a box only where the
        box can go on at once, and a box whose next module declines tries one detour first.
